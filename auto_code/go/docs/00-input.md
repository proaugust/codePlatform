# 需求结论（澄清确认）

## 摘要
用户最新明确要求：在现有 Go net/http 图书管理项目中增加修改图书接口，并在前端页面增加可见的编辑入口；此前该需求未生成成功、前端也看不到修改位置，本次需确保增量落地。项目已有列表、新增、删除与静态页面托管，本次只补修改闭环，不改成无关新系统。

## 目标
- 提供可用的修改图书后端接口，支持按 id 更新图书信息
- 在前端页面提供可见、可操作的图书编辑入口，保存后刷新列表
- 修复此前修改接口与前端编辑入口未生成成功的问题

## 范围
- 后端新增 PUT /api/books/{id} 修改接口，请求体包含 title、author、stock，id 以路径参数为准
- 修改成功返回更新后的图书数据；图书不存在返回 404 NOT_FOUND；非法 id 或校验失败返回 400 VALIDATION_ERROR
- 前端图书列表每行增加「编辑」按钮，点击后弹出编辑表单并预填当前图书信息
- 前端编辑表单保存时调用修改接口，成功后关闭表单并刷新图书列表，失败时展示错误信息
- 保留并兼容现有列表、新增、删除接口及根路径静态页面托管
- 保留 GET /health 健康检查

## 不在范围
- 不重写为无关的新系统或更换技术栈
- 不引入用户登录、权限与多租户能力
- 不做图书封面上传、分类标签等本期未提出的扩展功能

## 非功能
- 沿用 Go net/http 标准库实现，不引入重型框架
- 接口返回统一 JSON 结构与错误码（VALIDATION_ERROR、NOT_FOUND）
- 前端与后端同端口托管，静态页面可直接访问
- 修改操作需做基本输入校验，非法 id 与空标题等给出明确错误
- 保持与现有删除、新增接口风格一致，便于前端复用

## 待决问题（确认时已接受）
- 修改接口是否严格采用 PUT /api/books/{id}，请求体仅 title、author、stock（id 以路径为准）
- 前端编辑入口是否采用列表每行「编辑」按钮加弹窗表单的形式
- 图书数据存储仍为内存还是需要持久化尚未最终确认
- 服务端口存在 8080 与 8072 的冲突信息，需最终确认访问地址
- 新增图书时 id 是否由后端自动生成（前端不传 id），以彻底避免 VALIDATION_ERROR

## 用户硬需求（最高优先级，必须体现在 docs/计划/代码中）
- 增加一个修改图书的接口，前端页面也加这个
- 增加一个修改图书的接口没有生成成功，前端也没看到修改的地方
- 增加一个修改图书的接口没有生成成功，前端也没看到修改的地方
- 增加一个修改图书的接口，前端页面也加

## 会话滚动摘要
会话目标：从零生成一个 Go net/http 图书管理项目，由后端托管静态页面，前端可选择图书并调用后端删除。当前状态：代码已生成/更新，后端文件 11 个，前端生成成功；冒烟测试中创建图书返回 HTTP 201 并带回 id=1 的数据，但冒烟脚本把 201 误判为失败（创建失败 HTTP 201），需修正冒烟断言。已确认决策：业务范围为图书管理；前端与后端同端口托管；保留 GET /health；删除接口为 DELETE /api/books/{id}，成功 204、图书不存在 404 NOT_FOUND、非法 ID 400；删除后前端刷新列表并做二次确认；新增图书时 id 校验要求为大于 0 的整数，否则返回 VALIDATION_ERROR。待决问题：新增图书的 id 应由后端自动生成还是前端手动填写尚未确认（当前报错源于 id 被当作必填且须大于 0）；除删除外首版是否还需查询、修改等其他操作；图书数据用内存还是持久化存储未定；端口存在冲突信息，早期为 8080，最新计划写为 8072（http://localhost:8072/），需最终确认。注意：计划文本中误写为「写 Java/前端代码」，实际应为 Go/前端代码；执行生成不会自动启动进程，需在「运行」页启动。

## 硬约束
- 必须提供 GET /health
- 若工程已存在：默认增量修改，禁止无故改成无关新业务系统
- 用户硬需求中的接口（如 DELETE 图书）必须出现在 API 文档与实现中
