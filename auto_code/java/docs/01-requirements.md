# 总需求

## 背景
现有 Java/Spring Boot 图书管理后端工程（`auto_code/java`）在运行阶段出现报错，用户未提供异常堆栈与复现步骤。同时用户明确提出新增「删除图书」接口，供前端选择指定图书后由后端执行删除。

## 目标
1. 修复后端运行报错，使应用可正常启动并稳定提供服务（含 `GET /health`）。
2. 新增删除图书接口 `DELETE /api/books/{id}`，支持前端按 ID 删除指定图书。
3. 补齐全局异常处理与关键日志，使错误可定位且不泄露敏感信息。
4. 建立可复现、可验证的排障与回归基线。

## 范围
- 启动阶段问题：依赖冲突、配置缺失/错误、Bean 装配失败、数据源连接失败、端口占用等。
- 接口调用阶段问题：参数校验、空指针、序列化、事务与全局异常处理缺失等。
- 新增删除图书接口（Controller-Service-Repository 全链路）。
- 健康检查端点 `GET /health` 返回 `{status:ok}`。
- 回归验证：启动成功、健康检查正常、图书接口（含删除）冒烟通过。

## 不在范围
- 不新增除删除图书外的业务功能，不做架构级重构。
- 不做性能优化、压测、容量规划。
- 不修改现有对外 API 契约（除报错根因确在此处的最小必要调整）。
- 不涉及前端改动、生产部署与监控告警配置。

## 非功能
- 修复最小侵入、向后兼容，不破坏现有调用方。
- 不劣化启动时间与接口响应时间。
- 日志含请求标识与异常链，不输出密钥、密码等敏感信息。
- `GET /health` 轻量、不依赖外部强依赖组件，可被探针高频调用。
- 所有变更可回滚，变更点清晰记录。

## 假设
- 报错根因在启动阶段或现有图书接口调用阶段，按标准 Spring Boot 基线排查。
- 数据库使用 H2 内存库（基线约定），无需外部中间件。
- 删除图书采用物理删除；若图书不存在返回 404。
- 前端通过图书 ID 选择删除目标。
